# 0022 Collection architecture: headless-first, honest about refusal, authorised fallbacks

**Status:** Accepted (refines 0002, 0003, 0008, 0019)

**Context:** The collector must run unattended on Windows and on headless Linux, survive ordinary failures, and never lose collected data. It was investigated against the live site (2026-11-26) with one stock Chromium, no flags, no header/identity changes:

| Mode | Page load | Review-list API call | Result |
|---|---|---|---|
| headed | 200/202 (WAF script runs and passes) | returns reviews | 10 review cards |
| headless | 200/202 (same) | `ReviewsFrontendError: "Request not supported"`, `statusCode 400` | 0 cards |

The page, the browser build and our code are identical; the *server* answers differently for headless clients. That is an access restriction aimed at automated headless browsers, not a timing or rendering fault, so retrying cannot fix it. Defeating it would require changing the browser's identity (stealth patches, spoofed properties) or replaying internal endpoints, which ADR 0002 forbids.

**Decision:**
1. **Engine/IO split.** `engine.py` (retries, pacing, spool, checkpoints, stop rules) knows nothing about browsers; `browser.py` is the only Playwright code; `public.py` is pure parsing; `service.py` orchestrates and records history. Reliability is therefore unit-tested with fakes.
2. **Outcome classification** (`signals.py`): every failure becomes `transient | rate_limited | captcha | blocked | structure_changed`. Only the first two are retried (exponential backoff, jitter, `Retry-After` honoured and capped, `REVIEWHUB_COLLECT_MAX_ATTEMPTS`). `captcha`/`blocked` are decisions by the site: never retried, never solved.
3. **Circuit breaker + cooldown.** A `captcha`/`blocked` outcome stops all workers immediately (remaining properties are recorded as skipped, not requested). A scheduled run in the same browser mode within `REVIEWHUB_COLLECT_BLOCK_COOLDOWN_HOURS` (24) makes **no request** and records a skipped run, so a cron job cannot pound a site that said no. Exit code 6 lets a scheduler alert a human. A different mode is judged separately.
4. **Execution modes.** `--headless` (default, `REVIEWHUB_COLLECT_BROWSER_MODE`) and `--headed`. There is **no automatic fallback** from headless to headed after a refusal: that would be the collector routing around the refusal. On Linux, headed mode needs a real display and fails with a clear message otherwise. A virtual display (Xvfb) is deliberately *not* wired in: its purpose here would be to make a headless server look like a desktop to a site that refuses headless clients. An operator may run the CLI under a display they provide, as their own decision and responsibility; the code does not do it for them.
5. **Persistent sessions.** A per-worker browser profile directory (`REVIEWHUB_COLLECT_PROFILE_DIR`, default `data/collect/profile`) keeps the browser's own cookies/storage between runs; empty = ephemeral. Nothing is injected into it, it is git-ignored and never logged. Concurrent workers use separate profiles.
6. **Durability and resume.** Every page is appended and fsynced to a spool file (`data/collect/spool/<slug>__run<id>.jsonl`) *before* anything else. A property's spool is imported through the normal pipeline (fingerprint de-duplication) when it finishes, whatever its status, and deleted only after a successful import. A run that died leaves its spool; the next run imports it first and resumes at the last page read (24 h window; `--no-resume` disables). Heartbeat + `run_property.next_offset/last_page_hash` are updated per page; a reaped run stops at its next checkpoint and does not overwrite `abandoned` (ADR 0019).
7. **Pacing/concurrency.** Global jittered delays between page turns and between properties; `--concurrency` (1-3, default 1) runs parallel browsers but the pacer is shared, so request rate does not rise. DB writes are serialised.
8. **Duplicates.** Public pages expose no review id, so identity is the stable content fingerprint (property, date, rating, normalised text) from ADR 0003's pipeline. Overlapping pages and re-runs create nothing. Known limit: an *edited* public review looks new.
9. **History/logs.** `run` + `run_property` (queryable, `reviewhub runs list`) plus a per-run JSONL event log (`data/collect/logs/run-<id>.jsonl`): attempts, waits, outcomes, pages, circuit events. No cookies, headers, HTML or reviewer names.
10. **Authorised sources (browser-free, headless-safe).** `collect --source inbox` imports CSV/JSON exports dropped in `data/inbox/` (moved to `processed/` or `rejected/` with a reason). `collect --source feed` reads an owner-authorised HTTPS endpoint (`REVIEWHUB_COLLECT_FEED_URL` / `_TOKEN`) with the same retry policy; query strings never reach logs. These are the route to review-level data on a server while the public site refuses headless clients.

**Consequences:** On a headless server today, public-page collection reports `blocked` (verified live) and unattended review data comes from the inbox/feed. Headed collection on a desktop still works with the same engine. If the site's behaviour changes, no code change is needed: classification observes the outcome. The Terms of Service of the site also restrict automated access; that is a business decision for the operator and is stated in the README, not engineered around.
