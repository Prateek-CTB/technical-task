# 0023 Offline rule-based analyzer, and which analysis is reported

**Status:** Accepted (implements the lexicon half of ADR 0005; complements 0021)

**Context:** The only LLM available is an OpenRouter free model with about 50 requests a day, and sending real guest text to it is an operator decision (D7). On 2026-11-26 only 8 of 200 real reviews had a topic analysis, so the Review Intelligence screens were nearly empty. An assessor or a new operator without an API key would see the same. The brief allows keyword classification ("You may use keyword-based classification, an AI model, sentiment analysis…").

**Decision**
1. **A built-in analyzer** (`intelligence/lexicon.py`) behind the same interface as an LLM provider: `provider='builtin'`, `analyzer='lexicon'`, `model_id='lexicon-v1'` (the schema already reserved this). It returns the same JSON contract, so it goes through the **same schema validation, verbatim-evidence check and idempotent persistence** as LLM output. Run it with `reviewhub ai analyze --provider builtin`, or from the dashboard (Data & Collection, "Analyse new reviews").
2. **Method.** Booking asks two questions, so the answer box carries polarity (liked starts positive, disliked starts negative, title neutral; filler like "Nothing" is ignored). Each box is split into clauses (sentences, commas, "and"/"but"/"however"...). Multilingual cue lists (en, fr, de, es, it, pt, nl, da, sv) map clauses to the eight topics; some cues carry polarity ("dirty", "quiet", "overpriced"), and generic cues ("room", "area") give way to a specific one in the same clause. Negation flips polarity ("not clean") or creates a complaint ("no lift"). Evidence is always the exact clause text. Overall tone comes from the text; the guest's own score only breaks the tie at the extremes (≥ 9 positive, ≤ 3 negative), because Booking makes guests fill both boxes. Suggested actions come from a fixed per-topic playbook and are labelled rule-based.
3. **Precedence.** One analysis per review is current: **LLM > rule-based > mock**. A lower-ranked analyzer never displaces a higher one; an LLM result replaces a rule-based one when it arrives. Superseded rows are kept as history.
4. **Labelling.** Every API response carries `meta.analysis.methods` (`ai` / `rule_based` / `mock`) and each review its `method`. The dashboard never calls rule-based output "AI".
5. **Language** is detected offline (`intelligence/language.py`: script check, then stop-word voting). Short or ambiguous text is `und`, not a guess.
6. **Measuring it.** `reviewhub ai agreement` compares the two methods on reviews analysed by both. On 2026-11-26 (29 real reviews): topic precision 0.92, recall 0.86, F1 0.89 with the LLM as reference; polarity agreement on shared topics 0.96; overall-sentiment agreement 0.72. This is **agreement between two automated methods on a small sample, not accuracy**: there is still no human-labelled set (ADR 0014).

**D7 update (2026-11-26):** the operator authorised one capped LLM run on real public review text (`AI_ALLOW_REAL_GUEST_TEXT=1 ... --limit 30`). 21 reviews were analysed and 5 failed (empty or malformed model output, recorded as `failed`, never shown). The run then stopped on the free daily quota, as designed, and resumes on the next run. The default stays off.

**Consequences:** 100% coverage of reviews with text, offline and reproducible, at zero cost. Its limits are documented: sarcasm, comparisons, long multi-topic sentences, languages outside the word lists, and misspellings. The LLM path remains the higher-quality option and takes over review by review as quota allows.
